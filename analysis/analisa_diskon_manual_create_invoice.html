1. Latar Belakang & Kondisi Saat Ini

Saat ini, kolom diskon pada form Create Invoice bersifat readonly (tidak bisa diedit oleh user). Nilai diskon otomatis diambil dari tabel master ms_diskon berdasarkan:

  • Tipe produk (id_type dari ms_inventory_category3)
  • Term of Payment (id_top dari ms_top)

Flow Perhitungan Saat Ini

Master ms_diskon --> CariDiskon() via AJAX --> Nilai Diskon % (auto-fill)
     (per tipe produk + TOP)

Per Item:
  Total Harga  = Qty x Harga Satuan
  Nilai Diskon = Total Harga x (Diskon % / 100)
  Amount Item  = Total Harga - Nilai Diskon + Freight

Footer:
  Amount       = SUM(Amount Item)         <-- readonly
  Discount     = SUM(Nilai Diskon)        <-- readonly (dari master)
  Total        = Amount - Discount        <-- readonly
  Persentase   = % invoice                <-- editable
  Grand Total  = Total x Persentase%      <-- readonly
  DPP          = Grand Total              <-- readonly
  PPN          = DPP x PPN%              <-- readonly
  Total Inv    = Grand Total + PPN        <-- readonly

2. Masalah yang Ditemukan

⚠️ Problem #1: Perbedaan Basis Hitung (KG vs Sheet) — KRUSIAL

Ini adalah masalah paling kritis yang harus dipahami.
Produk di Metalsindo ada 2 jenis berdasarkan bentuk material:
• Reguler (Coil/Plate) → satuan KG
• Sheet (id_bentuk = B2000002) → satuan Lembar (Sheets)

Di Form Create Invoice (saat input):

Qty      = total_kirim (KG)      contoh: 2.500 KG
Per Unit = harga_deal (per KG)   contoh: Rp 10.000/KG
Amount   = 2.500 x 10.000       = Rp 25.000.000

Di Print Invoice (PDF yang dikirim ke customer):

Qty      = qty_sheet (lembar)       contoh: 500 Sheets
Per Unit = harga_satuan (per sheet) contoh: Rp 50.000/sheet
Amount   = 500 x 50.000            = Rp 25.000.000
Masalahnya: User di form create melihat basis KG, tapi customer di invoice melihat basis Sheet.

Jika user terbiasa menghitung diskon per-sheet (misal Rp 5.000/sheet x 500 = Rp 2.500.000), mereka tidak bisa langsung validasi angka tersebut di form create karena qty yang tampil adalah KG, bukan Sheet.

⚠️ Problem #2: Print Invoice Tidak Menampilkan Baris Diskon

Template PrintInvoice.php saat ini TIDAK menampilkan baris Discount. Footer PDF hanya:

| Total          | Rp 25.000.000 |
| DPP Nilai Lain | Rp 22.916.667 |
| PPN            | Rp  2.750.000 |
| Grand Total    | Rp 27.750.000 |

Meskipun diskon di-input, customer tidak akan melihat potongan diskon di invoice cetak.

⚠️ Problem #3: Halaman Index & Monitoring Tidak Memperhitungkan Diskon

Di model get_invoicing() dan get_monitoring_invoice(), nilai invoice yang ditampilkan TIDAK dikurangi diskon:

// Non-sheet:
$ttl_harga = SUM(qty_invoice x harga_satuan);  // tanpa kurangi diskon
$nilai_invoice = $ttl_harga + $ppn;

// Sheet:
$nilai_invoice += ($harga_satuan * $qty_sheet) + PPN;  // tanpa kurangi diskon
Akibat: Nilai di halaman index/monitoring bisa lebih besar dari yang seharusnya.

⚠️ Problem #4: Dampak ke E-Faktur / CoreTax

Di generate_efaktur(), DPP dihitung tanpa memperhitungkan diskon:

DPP = Qty x Harga Satuan (TANPA kurangi diskon)
DPP Nilai Lain = ceil(11/12 x DPP)
PPN = DPP Nilai Lain x 12%
Risiko: DPP yang dilaporkan ke pajak lebih besar dari nilai sebenarnya → potensi lebih bayar PPN.

⚠️ Problem #5: Update SPK Marketing Bisa Tidak Akurat

Saat save invoice, ada update akumulasi:

UPDATE tr_spk_marketing 
SET percent_invoice = percent_invoice + $percent,  
    total_invoice = total_invoice + $dpp  
WHERE id_spkmarketing = '$no_so'

Jika diskon manual mengubah DPP, monitoring persentase penyelesaian invoice di SPK Marketing bisa salah.

⚠️ Problem #6: Tidak Ada Audit Trail Diskon Manual

Saat ini tidak ada catatan:

  • Siapa yang mengubah diskon dari nilai master
  • Berapa diskon seharusnya (dari master ms_diskon)
  • Alasan pemberian diskon khusus

Kolom diskon_compare sudah tersedia di tr_invoice_detail tapi belum digunakan aktif.

3. Opsi Solusi

Opsi A: Input Diskon Nominal Total (Rp) di Footer

Field diskon di footer form dibuat editable. User input nominal total Rupiah langsung.

✔ Implementasi paling sederhana

✔ Tidak perlu ubah struktur database

✔ Solve masalah KG vs Sheet

✔ Universal semua tipe produk

✔ Controller tidak perlu diubah

✘ Tidak ada breakdown per item

✘ User harus hitung sendiri di luar sistem

Opsi B: Input Diskon Per-Item (Nominal Rp per Baris)

Setiap baris item ditambahkan kolom Diskon (Rp) yang bisa di-input manual.

✔ Granular - bisa trace per produk

✔ Akurat untuk e-Faktur

✘ Lebih complex

✘ Tetap ada masalah sheet vs KG

✘ Perlu ubah SaveNewInvoice()

✘ Perlu ubah JavaScript signifikan

Opsi C: Input Diskon Per-Item (Persentase %) Editable

Sama seperti sekarang (diskon %) tapi field dibuat editable, tidak lagi dari master.

✔ Perubahan minimal dari kondisi saat ini

✔ JS HitungTotal() sudah support

✔ Database tidak perlu diubah

✘ User harus convert nominal ke %

✘ Masalah sheet tetap ada

✘ Tidak intuitif untuk diskon flat

Opsi D: Hybrid (Total + Per Item Opsional)

Footer bisa di-input manual, opsional expand untuk detail per item.

✔ Paling fleksibel

✔ Solve masalah sheet vs KG

✘ Paling complex untuk implementasi

✘ UX bisa membingungkan

✘ Effort development tinggi

5. Rekomendasi: Opsi A (Input Diskon Nominal Total di Footer)

Rekomendasi: Gunakan Opsi A karena:
  1. Solve masalah KG vs Sheet — User input nominal final, tidak perlu bingung basis hitungnya
  2. Effort minimal — Hapus readonly, tambah JS recalculate, tambah validasi
  3. Tidak merusak yang sudah jalan — Controller SaveNewInvoice() tidak perlu diubah
  4. Konsisten — Berlaku sama untuk reguler, sheet, dan slitting

Detail Perubahan JavaScript

Tambah fungsi baru hitungDiskon():

function hitungDiskon() {
    var amount = getNum($('#totalproduk').val().split(",").join(""));
    var diskon = getNum($('#diskon').val().split(",").join(""));
    
    // Validasi: diskon tidak boleh > amount
    if (diskon > amount) {
        swal("Warning", "Diskon tidak boleh melebihi total Amount!", "error");
        $('#diskon').val('0.00');
        diskon = 0;
    }
    
    // Validasi: diskon tidak boleh negatif
    if (diskon < 0) {
        swal("Warning", "Diskon tidak boleh negatif!", "error");
        $('#diskon').val('0.00');
        diskon = 0;
    }
    
    var total = amount - diskon;
    $('#total').val(number_format(total, 2));
    $('#diskon').val(number_format(diskon, 2));
    
    hitungPpn();
}

Ubah fungsi totalBalanced():

function totalBalanced() {
    var SUMx = 0;
    $(".total").each(function() {
        SUMx += Number($(this).val().split(",").join(""));
    });
    
    $('#totalproduk').val(number_format(SUMx, 2));
    hitungDiskon(); // trigger recalculate dengan diskon
}

Ubah fungsi hitungPpn():

function hitungPpn() {
    var total = getNum($('#total').val().split(",").join("")); // pakai Total (setelah diskon)
    var ppn = $('#ppn').val();
    var persentase = $('#persentase').val();

    var nilai_tagih = (getNum(total) * getNum(persentase)) / 100;
    var nilai_ppn = (getNum(nilai_tagih) * getNum(ppn)) / 100;
    var nilai_invoice = getNum(nilai_tagih) + getNum(nilai_ppn);

    $('#grandtotal').val(number_format(nilai_tagih, 2));
    $('#dpp').val(number_format(nilai_tagih, 2));
    $('#totalppn').val(number_format(nilai_ppn, 2));
    $('#nilai_tagih').val(number_format(nilai_invoice, 2));
}

6. Skenario Penggunaan

Skenario 1: Produk Reguler (KG) dengan Diskon Negosiasi

Situasi: Customer PT ABC beli coil 5.000 KG @ Rp 15.000/KG. Negosiasi dapat diskon Rp 5.000.000
TahapFieldNilai
Form CreateAmount5.000 x 15.000 = Rp 75.000.000
Form CreateDiscount (user input)Rp 5.000.000
Form CreateTotalRp 70.000.000
Print InvoiceQty / Per Unit / Amount5,000.00 Kgs / 15,000.00 / 75,000,000.00
Print InvoiceDiscount5,000,000.00
Print InvoiceSub Total70,000,000.00

Skenario 2: Produk Sheet dengan Diskon Per-Lembar

Situasi: Customer PT XYZ beli sheet 500 lembar (total berat 2.500 KG). Harga per KG = Rp 10.000. Diskon dari sales: Rp 2.000/sheet = 500 x 2.000 = Rp 1.000.000
TahapFieldNilai
Form Create (basis KG)Amount2.500 x 10.000 = Rp 25.000.000
Form CreateDiscount (user input nominal)Rp 1.000.000
Form CreateTotalRp 24.000.000
Print Invoice (basis Sheet)Qty / Per Unit / Amount500.00 Sheets / 50,000.00 / 25,000,000.00
Print InvoiceDiscount1,000,000.00
Print InvoiceSub Total24,000,000.00
Mengapa ini bekerja: User input Rp 1.000.000 (sudah dihitung sendiri: 500 sheet x Rp 2.000). Customer di invoice lihat diskon sebagai nominal total. Tidak ada konflik basis KG vs Sheet.

Skenario 3: Tanpa Diskon (Default)

Situasi: Invoice tanpa diskon. User biarkan field = 0 atau kosongkan.

Di Print Invoice, baris Discount TIDAK ditampilkan (conditional: hanya muncul jika diskon > 0).
