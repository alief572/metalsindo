# Audit UI Report Incoming

Tanggal: 12 Oktober 2026 (Asia/Jakarta).
Mode: after, pilihan pengguna pada sesi ini.
Lingkup: view dan CSS report_incoming, definisi kolom model, serta kontrak md/report_incoming/SPEC.md.
Metode: pemeriksaan source dan perhitungan kontras; tidak menguji browser atau database. Screenshot modul Incoming tidak tersedia, sehingga tidak menyatakan temuan visual runtime.

Prioritas mengikuti tier antislop: Hard Gate = HIGH, Purpose-Gate = MEDIUM, Quality Locks = LOW. Angka prioritas tidak menunjukkan urutan manfaat visual.

## Temuan bernomor

### 1. HIGH: placeholder dan batas input kurang kontras (R-25)

Alasan: pencarian serta input tanggal sulit dibedakan dari permukaan panel.

Bukti: assets/css/report_incoming.css:20-21 memakai placeholder #687b8b pada #f6f9fb dengan kontras 4.14:1, di bawah 4.5:1 untuk teks normal. Inset border rgba(25,84,114,.12) pada isi input menghasilkan sekitar #dbe5eb, dengan kontras 1.21:1 terhadap isi input dan 1.28:1 terhadap putih. antislop-human memerlukan 3:1 untuk batas kontrol. Nilai ini berasal dari CSS modul, bukan computed styles browser.

Usulan: gelapkan placeholder dan beri border solid yang cukup jelas, mengikuti kualitas kontrol yang sudah diperbaiki pada LHP Slitting.

### 2. HIGH: pemilih jumlah baris belum memenuhi ukuran sentuh (R-03)

Alasan: kontrol untuk membaca laporan masih memakai ukuran desktop kecil.

Bukti: assets/css/report_incoming.css:41 menetapkan tinggi select 34px tanpa pembesaran pada mobile; pagination pada baris 54 dan 70 juga tidak menetapkan target minimum 44px. Ukuran aktual pagination belum diukur.

Usulan: minimum 44px untuk select dan pagination; beri jarak antarhalaman serta wrapping agar pagination tidak memaksa lebar halaman.

### 3. HIGH: empty state tidak menunjukkan tindakan berikutnya (R-27)

Alasan: pengguna tidak diberi arahan ketika penerimaan belum tersedia atau filter menghasilkan nol baris.

Bukti: application/modules/report_incoming/views/index.php:80 hanya memuat "Belum ada data Incoming." dan "Tidak ada hasil sesuai filter." Loading dan error sudah mempunyai pesan tersendiri.

Usulan: jelaskan perlunya pencatatan Incoming material supplier untuk data kosong; untuk filter kosong, sarankan mengubah periode/kata pencarian atau memakai Reset.

### 4. MEDIUM: heading filter mengulang kategori laporan (R-06, R-09)

Alasan: Warehouse report dan badge kategori mengambil perhatian tanpa menambah informasi yang membantu membaca hasil.

Bukti: view baris 8-9 memakai eyebrow Warehouse report dan badge Incoming material supplier; CSS baris 13 memakai 10px, uppercase, serta tracking 1.4px untuk eyebrow. Jenis laporan sudah diketahui dari halaman dan kontrak modul.

Usulan: hapus eyebrow dan pill kategori; pertahankan informasi lingkup supplier sebagai teks bantuan bila diperlukan. Jumlah hasil tetap ditampilkan karena bersumber dari server.

### 5. MEDIUM: panah dan animasi dekoratif mengganggu hierarki tindakan (R-08, R-19)

Alasan: submit filter tidak memerlukan panah berlingkar, dan gerak ikon ekspor ke kanan tidak menjelaskan unduhan.

Bukti: view baris 16 dan 25 memakai incoming-button-icon; CSS baris 8, 24-25, 31-33, dan 62 mengatur animasi masuk, transform tombol, dan pergeseran ikon. Reduced motion sudah tersedia, tetapi tujuan gerak tidak ditemukan dalam dokumen modul.

Usulan: tombol Tampilkan laporan berbasis teks, ekspor mempertahankan ikon unduh yang relevan, dan feedback memakai warna/fokus tanpa animasi panel.

### 6. MEDIUM: panel memakai bingkai dan bayangan berlapis (R-12)

Alasan: filter dan tabel sama-sama mendapat elevasi dekoratif sehingga perbedaan perannya kurang jelas.

Bukti: CSS baris 8-9 memberi shell padding 5px, background, radius 15px, inset shadow, lalu panel radius 11px dan shadow lain. Tidak ditemukan alasan elevasi khusus dalam dokumentasi report_incoming.

Usulan: satu permukaan dengan border sederhana; gunakan ukuran heading dan kepadatan isi untuk membedakan filter dari hasil.

### 7. LOW: ruang filter besar sementara teks tabel kecil (R-05, R-06)

Alasan: laporan dengan 19 kolom memerlukan ruang dan keterbacaan yang lebih baik daripada dekorasi panel.

Bukti: CSS baris 9-10 memakai padding panel 24px dan margin heading 24px; header tabel 11px, isi 12px, dan padding sel vertikal 13px pada baris 43-46. Semua header diberi minimum 135px, termasuk kolom nomor urut yang pendek. Caption Detail penerimaan material pada view baris 26 mengulang heading Hasil incoming.

Usulan: rapatkan filter/toolbar, hilangkan caption berulang, naikkan ukuran teks dengan padding baris lebih kecil, dan alokasikan lebar sesuai isi: nomor urut sempit, Supplier/Material/Customer lebih lapang. Tambahkan keadaan layout menengah, mengikuti pola LHP Slitting yang sudah diperbaiki. Pertahankan 19 kolom, urutannya, dan scrollX; tidak mengusulkan kartu statistik atau grand total.

### 8. LOW: petunjuk penting tentang progress PO berada setelah tabel (R-05, R-31)

Alasan: pengguna dapat menafsirkan angka berulang sebagai nilai tiap lot sebelum melihat peringatannya.

Bukti: view baris 34 menempatkan catatan Total Qty Receive dan Balance setelah tabel. Kontrak SPEC.md menyatakan kedua nilai adalah progress item PO terkini, berulang per lot, dan tidak dihitung ulang oleh filter tanggal. Catatan juga memuat arti Belum terverifikasi serta sifat historis Customer.

Usulan: tampilkan peringatan angka berulang serta pengaruh filter tanggal sebelum tabel; susun penjelasan PIC/Surat Jalan dan Customer agar mudah dibaca tanpa menghilangkan makna historisnya.

## Hal yang sudah baik

- Jumlah penerimaan memakai recordsFiltered dari server.
- Handler filter, Reset, dan ekspor memiliki endpoint nyata dalam source.
- Guard draw pada xhr menjaga respons lama agar tidak mengganti status hasil terbaru; tetap pertahankan saat implementasi.
- Loading/error/empty states tersedia dan tanggal awal melebihi akhir ditolak.
- Kolom numerik rata kanan dan tabular numerals, tanggal memiliki class tersendiri, dan scrollX tersedia.
- Teks utama #385468 pada putih mempunyai kontras 7.97:1; teks sekunder #607486 mempunyai 4.84:1. Temuan kontras tidak berarti seluruh teks modul gagal.
- Kontrak menjelaskan satu detail penerimaan/lot per baris, progress PO tersimpan, ambigu PIC/SJ, dan Customer historis. Perbaikan UI harus mempertahankan penjelasan tersebut.

- PASS: rasio dihitung dengan fungsi contrast-check.py dari antislop-human.
- PASS: delapan temuan mempunyai aturan, prioritas, bukti, dan usulan.
- PASS: hanya file audit ditambahkan; UI dan konfigurasi yang sudah berubah tidak disentuh.

## Risiko dan tindak lanjut

Tidak mengklaim browser, mobile, keyboard, zoom, ekspor, atau computed styles telah diuji. Horizontal scroll tabel tidak otomatis berarti overflow halaman. Tidak mengaudit ulang kebenaran mapping dan query produksi. Tidak ditemukan DESIGN.md khusus report_incoming; arah perbaikan dapat mengikuti laporan operasional biru Metalsindo dari LHP Slitting, dengan alasan keputusan ditulis sebelum implementasi.

Sesuai mode after, pengguna memilih nomor temuan yang diperbaiki sebelum source UI diubah. Rekomendasi: semua 1-8 agar kedua modul laporan konsisten.
